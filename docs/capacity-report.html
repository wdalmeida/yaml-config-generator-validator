The distinction everything rests on

A connection is not a request

1 000 connections does not mean 1 000 req/s. A keepalive connection carries thousands of sequential requests — it stays open and keeps going. Connections say how many conversations are open at once; req/s says how fast the words move.

Sockets used: 4 (for perfect keepalive, would be 4) Code 200 : 305 370 (100.0 %) ← 4 connections, 305 370 requests

At 1 000 connections and — req/s, each connection receives about — req/s — one request every — ms. A concurrent user is different again: a browser opens ~6 connections per host, a cold page load is ~4 requests, and most of a reader's time is spent not fetching anything.

What concurrency and CPU actually buy

The cliff

Memory is not a dial, it is a cliff

CPU is a dial: below what it needs, the service slows down but serves every request. Memory is not: below what it needs, the kernel kills the container mid-response. At rest the pod fits in 5 Mi, which makes a small limit look entirely safe — and that is the trap.

Limit Concurrency Throughput Result

Peak observed working set is 36 Mi at 100 connections. The transient buffer demand of streaming a large file to many connections at once is what no steady-state reading shows you. More CPU makes memory worse: at 1 000m the pod serves fast enough to hold far more responses in flight than at 500m, and 1 000m is exactly where 128 Mi dies.

Sizing

What to set, per target concurrency

The cheapest limits that don't cost you latency at each level. Requests stay at cpu: 10m / memory: 32Mi throughout — those are what the cluster actually reserves, and the pod idles near zero.

500m is the right CPU for almost everything — three rows out of four. Below it the tail degrades sharply; above it, throughput per millicore collapses, and it is the only setting that was ever OOMKilled. The memory column is a floor plus margin rather than a target: 64 Mi is measured clean at 100 connections, which bounds everything below it, and only the 1 000-connection row needed its own measurement.

The answer

The best balance at 1 000 connections

Recommended

cpu 500m · memory 256Mi

  • Doubling CPU from 500m to 1 000m buys only +23% throughput (13 057 → 16 051 req/s). That is the worst-value step on the curve; below it, 250m → 500m more than doubles throughput for the same doubling of CPU.
  • 500m never triggered an OOM, even at 128 Mi. The only OOM in the whole campaign was at 1 000m — the faster the pod, the more responses it holds in flight, and the more buffers it consumes.
  • The median is already excellent at 500m: 2.9 ms against 2.6 ms at 1 000m. The difference is entirely in the tail, and at this concurrency the tail is dominated by queuing, not by CPU.
  • 256 Mi rather than 128 Mi, confirmed rather than assumed: at 1 000 connections, 128 Mi was killed in 4 runs out of 5 and 256 Mi held 3 out of 3. Unused memory costs nothing at runtime — only the request reserves capacity, and that stays at 32 Mi.
resources:
  requests:
    cpu: 10m          # what the cluster actually reserves
    memory: 32Mi
  limits:
    cpu: 500m         # ~13 000 req/s at 1 000 connections
    memory: 256Mi     # 128Mi dies at this concurrency

If cost matters more than latency, 250m / 256Mi still serves 5 613 req/s at 1 000 connections with zero errors — at ~4 requests per cold page load, roughly 1 400 page loads a second.

Before you quote any of this

Limits of the measurement

  1. The load generator shares the node. fortio runs in the same 4-vCPU cluster, so absolute throughput is a floor rather than a capacity rating. The shape of the curves and where things break is what transfers.
  2. One replica. Every figure is per pod. The chart deploys two by default.
  3. Cold load. Every request fetches the full bundle. A real browser caches it and afterwards asks only for index.html, so capacity in real users is far higher.
  4. nginx forks one worker per node CPU, not per CPU limit — 4 here, 64 on a 64-core node. The base image's autotune script cannot fix that under readOnlyRootFilesystem, which forbids it from rewriting nginx.conf.
