# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static site (no backend) that walks users through onboarding: first an **Onboarding** checklist of the steps to follow, then the things those steps produce — the YAML config files our software requires in its repository, filled out and validated here so they stop hand-editing them incorrectly, plus the **Kubernetes** resources for their namespace. Supports multiple independent file types in parallel — Tenant Config (`config.yaml`), CI (`ci.yml`), CD (`cd.yml`), Env (`env.yml`), Protection (`protection.yml`) — switchable via the pill strip at the top, each with its own schema and its own in-progress draft (persisted to `localStorage`, so switching types never loses work).

**The checklist itself produces no file, and neither pill that isn't a config type follows the two-column layout blindly.** Onboarding is a single centred column of steps (there is nothing to render beside them — a step's output is a config pill or the Kubernetes pill, each with its own YAML), and Kubernetes is one-way: two inputs in, a read-only rendered manifest stream out, copied rather than pushed. **Each step is written twice**, once for the terminal and once for the web console, and a persisted CLI/UI switch shows one and hides the other — see below.

Each config type is one two-column screen (`ConfigWorkspace`), not separate Generate/Validate tabs: the **left column** is pure input - target file location (owner/repo/branch, plus the fixed filename stated as text) and the schema's own fields - and scrolls normally, however long the form gets. The **right column** is one unified, bidirectional YAML field (a lazy-loaded CodeMirror editor, see below) plus every action that operates on its content - Fetch from GitHub (header, pulls content in before editing), Copy YAML and Push to GitHub (footer, get content back out once it's ready) - grouped together since they're all "do something with this YAML," not "configure the target." The panel is `position: sticky` so it stays pinned in view the whole time rather than scrolling out of sight past a long form (below the 860px breakpoint, where the columns collapse to one, it's no longer sticky - there's no second column left for it to stay pinned against). Editing a form field updates the YAML field live; editing/pasting into the YAML field itself validates live and, only once valid, syncs back into the form fields — there's no separate "paste box" or manual Validate/Load step, and no manual Copy vs. Output distinction either.

**The CI/CD/Env/Protection schemas are placeholders** (`src/configs/schemas/{ci,cd,env,protection}.schema.json`) — guessed field lists, not yet confirmed against the real config specs. Expect to replace their fields; `tenant-config.schema.json` is the one built from real requirements. **The shipped onboarding steps are placeholders too** (`src/onboarding/tenant.onboarding.json`) — a plausible shape with `example.com` docs URLs and invented `PLAT-` ticket keys, pending the real process. **So is the Kubernetes RBAC** (`src/kubernetes/manifests.ts`) — the resource *shape* is what was specified, but the Role's rules, the two service account names and the token Secrets are guesses, each marked `# TODO: confirm` in the rendered output itself so the warning survives a copy/paste into a terminal. See `docs/kubernetes-resources.md`.

                      # our own checked-in meta-schema + every `config` action's configId
                      # actually naming a pill that exists
npm run lint:md       # markdownlint-cli2 on every *.md file (.markdownlint-cli2.jsonc)

The last four `lint:*` scripts above are thin aliases for `go run ./tools/cmd/<name>` — see
**The `tools/` Go module** below. They stay under `npm run` because that is where every other
check in this repo lives, and CI calls the `go run` form directly.

```sh
go build ./... && go vet ./... && go test ./...   # the tools/ module (`just go` runs all three)
gofmt -l .                                        # must print nothing
go run ./tools/cmd/scan-gate osv <report.json>    # the severity gate, on a scanner's JSON
```

`justfile` (+ `Brewfile`) is the local replica of the workflows below — `just ci`, `just supply-chain`, `just container` run the same tools with the same flags and report every job pass/fail rather than stopping at the first failure, and each aggregate is also available one recipe at a time (`just lint`, `just zizmor`, `just image-smoke`, …). Two things keep it from drifting out of sync with CI: **every tool version is grepped out of the workflow file that pins it** (the same strings `renovate.json`'s custom regex managers match, so a weekly bump lands locally for free — `just doctor` reports what's installed against those pins, `just install-pinned` fetches an exact pinned build, checksum-verified, into `.ci-tools/bin`), and every recipe mirrors one workflow step, with the runner-only parts (SARIF upload to code scanning, Sigstore attestation, the GHCR publish) named as skipped rather than faked. One tool cannot be baked into the devcontainer image: `install-pinned kube-linter` reads its asset digest from GitHub's release API (it publishes no checksums file) and so needs an authenticated `gh`, which an image build doesn't have — run it once inside the running container. `just install` uses Homebrew for everything it can (`Brewfile`) — plumber is the exception, since Homebrew refuses to load its third-party tap without an explicit `brew trust` and that tap tracks a newer release than `ci.yml` pins anyway, so it comes from the pinned checksum-verified download instead. Reports/SBOMs/archives are written to `.ci-out/` (gitignored, summarised by `just artifacts`) rather than the repo root, so nothing collides with what CI writes. **There is deliberately no duplicated logic left between the two.** There used to be: `container.yml`'s fixable-HIGH/CRITICAL OSV gate was ~35 lines of Python re-stated verbatim in `just image-sca`, with a "change one, change the other" comment on each copy, because that job downloads artifacts without checking the repo out and so had no script file to share. Both now run `go run ./tools/cmd/scan-gate osv <report.json>` — the job sparse-checks-out `tools/` beside its acceptance file, which is what made one copy possible. If a future recipe cannot call the same command the workflow does, that is a reason to make it able to, not to copy the logic.

`.devcontainer/` (`Dockerfile` + `devcontainer.json`, documented in `docs/devcontainer.md`) is that same toolchain prebuilt on Node 24, plus podman/buildah/skopeo and two agent CLIs (Claude Code, opencode). It carries **no list of tool versions of its own**: the build copies in `justfile` and `.github/workflows` and runs `just tools_dir=/usr/local install-pinned <tool>` for each one, so the image installs whatever the workflows currently pin and a rebuild tracks Renovate for free. Only the three tools that must exist before `just` can run — `just` itself, `uv`, `gh` — are pinned there, as `ARG`s annotated with `# renovate:` comments (renovate.json's devcontainer-tools manager; deliberately *not* automerged, unlike the workflow tool group, since no CI job builds this image). Claude Code and opencode are intentionally unpinned — Claude Code self-updates at runtime, so a pin would be fiction. The one CI check that does cover the file is `container.yml`'s hadolint job, which lints it alongside `Containerfile`. `runArgs` is `["--privileged"]` because `just container` builds a container from inside the container: without it the nested user namespace can't be mapped (`newuidmap: Operation not permitted`), and capabilities alone don't substitute (tested) - the official docker-in-docker feature needs the same flag. Verified end-to-end (real `image-build` + `image-smoke`) on both a rootless podman host and rootful podman, the latter being the same not-in-a-userns model dockerd uses. Note `.ci-tools/` is platform-scoped (`.ci-tools/<os>-<arch>/bin`) precisely because the workspace is shared with this container: a macOS binary ahead of the container's own on `PATH` is a genuinely confusing failure (it was hit while building this).

Linting uses **oxlint**, not eslint — config is `.oxlintrc.json`. Plugins enabled: `react` (includes `rules-of-hooks`, `jsx-key`, etc.), `typescript`, `oxc`, and `jsx-a11y` (static accessibility linting - missing `alt`, unlabeled form controls, ARIA misuse), with six a11y rules promoted from warning to **error** since the codebase is clean of them.

**Accessibility is checked three ways, and the jsx-a11y layer above is only the first** — see `docs/accessibility.md`. The target is WCAG 2.2 AA. `src/App.a11y.test.tsx` runs **axe-core** over the real rendered trees (every pill, every config type — iterating the registries, so a new `.schema.json` is covered the day it lands), `src/App.contrast.test.ts` computes contrast ratios straight out of `src/App.css` for both themes, and `src/App.colorblind.test.tsx` simulates protanopia/deuteranopia/tritanopia (Machado et al. matrices) and measures CIEDE2000 between the colours that encode mutually exclusive states — contrast and colour vision are different questions, and two colours can each clear 4.5:1 against the background while being indistinguishable from each other. The shared maths is `src/test-color.ts` (test-only, never bundled). That middle layer was the gap this file used to describe as an acceptable one, and it was not: `FieldRow` rendered its `<label>` as a **sibling with no `htmlFor`**, so it named nothing and **7 of the 12 controls on the Tenant Config screen had no accessible name**. jsx-a11y does not catch it — `label-has-associated-control` fires on that shape written inline, but the label and control here are assembled by a helper function. Reintroducing the bug fails five axe tests while `npm run lint` still exits 0. Things worth not undoing: **`--success` is a teal, not a green** (against the amber beside it, green measured CIEDE2000 **8.6** simulated for protanopia where ~11 is the floor for reliable discrimination — the test fails on it by name), **the pill status is a shape before it is a colour** (`StatusEmptyIcon`/`StatusDraftIcon`/`StatusValidIcon` — a ring, a half-ring and a tick; that survives monochromacy, greyscale printing and a washed-out projector, which no palette choice does), **`--accent` and `--accent-strong` are not redundant** (the brand orange is 2.99:1 as text and fine as a border — the contrast test asserts the split itself), **`.visually-hidden` is not `display: none`** (that would remove it from the accessibility tree, the opposite of the point), single controls get `useId` + `htmlFor` while **groups get `fieldset`/`legend`** (a label may name exactly one control), and the pill strip is `aria-current="page"` rather than `role="tab"` deliberately — the tab role obliges arrow-key roving focus and `aria-controls`, a contract these view-switching buttons don't implement. `vite.config.ts` sets `test.css: true` purely so the contrast test's `?raw` import of `App.css` isn't stubbed empty.

**The theme is a three-way Auto/Light/Dark switch** (`src/components/ThemeSwitch.tsx`, `src/lib/theme.ts`, persisted under `theme`). Auto is the **absence** of `data-theme` on `<html>`, not a third value — the CSS keys off that absence so `prefers-color-scheme` keeps doing the work and the page follows the OS mid-session; writing `data-theme="auto"` would match neither rule. The dark palette is therefore **declared twice** in `App.css` (inside the media query guarded `:not([data-theme='light'])`, and again as `:root[data-theme='dark']`) because CSS cannot share a declaration block between a media query and a plain rule, and `light-dark()` would resolve to nothing on a browser that doesn't know it — taking the whole palette down rather than degrading. `App.contrast.test.ts` asserts the two copies are identical so they can't drift. `main.tsx` applies the stored choice **before the first render**, not in an effect: an effect runs after paint, and the usual inline-`<script>` fix is unavailable because `container/nginx.conf`'s CSP is `default-src 'self'` with no `unsafe-inline` for scripts. **There is deliberately no colourblind palette mode** — the states already carry shape and text, the only pairs it could improve aren't contrastive, and a mode behind a setting most people never find is how the default stays mediocre. `src/App.layout.test.ts` guards the scroll declarations (`.yaml-panel { overflow: hidden }` plus `.yaml-editor-host { flex: 1 1 240px; min-height: 0 }` — a flex item won't shrink past its `min-height`, and the old hard `240px` floor is what made the sticky panel spill its contents past its own edge with nothing to scroll them); it explicitly cannot assert that anything scrolls, since jsdom does no layout.

Seven workflows in `.github/workflows/`, every `uses:` pinned to a full commit SHA with a `# vX.Y.Z` comment (not even a floating major-version tag — those are mutable too; Semgrep's `p/security-audit` ruleset in `supply-chain.yml`'s `sast` job enforces this) — see `docs/supply-chain-security.md`:

- `ci.yml` — **every job here is gated on what the PR actually touched** (see "Scoping CI to the files a change can affect" below): `test` (lint, build, `lint:size`, test-with-coverage - uploaded as an artifact), `schemas` (`lint:schemas`), `go` (`gofmt`/build/vet/test over the `tools/` module - see below), `markdown` (`lint:md`), `links` (`lint:links`, relative links only - external URLs moved to `link-check.yml`), `audit` (`npm audit --audit-level=high --package-lock-only`, no `npm ci`: it resolves from the lockfile), `renovate` (`renovate.json` through Renovate's own `renovate-config-validator` - nothing else in CI reads that file, so without this the only feedback on a typo is Renovate opening a Config Warning issue *after* the merge. It is the official validator rather than a schema check because the config has semantics no JSON Schema expresses, and it is bucket-gated because it pulls ~600 packages for one file that changes a handful of times a year), `actionlint` (lints the workflow YAML files themselves - install via the [official script](https://github.com/rhysd/actionlint), same as `brew install actionlint` locally; no native SARIF output, so this stays a plain pass/fail check), `gitleaks` (secret scanning - runs the FOSS `gitleaks` CLI directly, downloaded and checksum-verified in-job, **not** the `gitleaks/gitleaks-action` wrapper, which is a separate proprietary product under its own EULA despite the CLI itself being MIT; also runs locally as a pre-commit hook, so the CI job is defense-in-depth for PRs from forks where the hook isn't installed), `zizmor` (GitHub Actions-specific security linter, `pip install zizmor` - catches template injection, overly broad workflow permissions, and credential persistence through `checkout` that neither `actionlint` nor Semgrep's generic rulesets check for; run locally with `uvx zizmor .` before editing any workflow file), `plumber` (a second, independent GitHub Actions security scanner, MPL-2.0/FOSS, via the official `getplumber/plumber` action - different engine/ruleset from `zizmor`: exposed/unmasked secrets, mutable remote-code execution nested inside third-party actions, known-CVE action versions, branch protection - self-contained, so it handles its own SARIF/artifact upload rather than needing the second-run treatment below; blocking by default (min-points 100, any finding fails) - scores 100/100, see `docs/supply-chain-security.md` for the one real finding it caught and how it was fixed). The `test`, `markdown`, `gitleaks`, and `zizmor` jobs each additionally run their tool a second way (`oxlint --format=sarif`, `markdownlint-cli2`'s SARIF formatter — see `.markdownlint-cli2.jsonc`'s `outputFormatters` —, `gitleaks ... --report-format=sarif`, and `zizmor ... --format=sarif`) and upload the result both as a downloadable artifact and to Security → Code scanning (`continue-on-error: true` on the upload-sarif step, since code scanning requires GitHub Advanced Security on private repos - this shouldn't fail CI on a repo without it). **Which of the two runs is the gate is not a free choice: it depends on whether the tool's SARIF mode still exits non-zero on findings.** markdownlint, gitleaks and kube-linter do, so one run is both report and gate, taken from its `outcome`. `zizmor --format=sarif` exits **0** regardless, so its job runs the plain form as the gate and the SARIF form with `if: always()` as the report — the shape oxlint already used. It did not always: the zizmor job gated on the SARIF run's `outcome` until that was found to be unfireable, and two real findings had been sitting unreported behind it. Check this before adding a fifth tool to the pattern; `just <tool>` reads the plain form's status, so a divergence shows up as the local recipe being stricter than CI. Every `actions/checkout` step across every workflow sets `persist-credentials: false` (flagged by `zizmor`'s `artipacked` audit) since no job here needs the checked-out git credential to push anything back.

Renovate needs its GitHub App installed on the repo to actually run - that's a manual one-time step, unlike Dependabot.

Two repository rulesets (not workflows - live repo settings, see `docs/releasing.md`) enforce: `v*` tags are immutable (update+deletion blocked, admin bypass only) once created, and `main` requires a PR with passing status checks before merge (no approval count required - solo maintainer - same admin bypass).

**Scoping CI to the files a change can affect.** A README typo used to run the same ~20 jobs as a change to `src/`. It no longer does, and the mechanism is split in two because **workflow-level `paths:` filters and required status checks are mutually exclusive**: a workflow skipped by a path filter never creates its check runs at all, so a required check sits *Pending* forever and the PR can never merge.

- **`deploy.yml` uses a plain `paths-ignore:`** — safe precisely because none of its checks are required, and it is main-only with `workflow_dispatch` as an unfiltered escape hatch. **That is a standing constraint, not an accident**: making it required means first giving it the in-workflow gating below. The lists are duplicated across `push` and `pull_request` (Actions has no YAML anchors) and actionlint will not catch them drifting. `supply-chain.yml` gained a weekly cron in the same change — everything it reports is time-dependent, so filtering it without one would let the npm SCA path go quiet on a repo whose lockfile hasn't moved; `container.yml` already had one for the same reason.
- **`container.yml`, `supply-chain.yml` and `codeql.yml` gate from the inside too**, each fronted by its own always-running aggregate (`container-ok`, `supply-chain-ok`, `codeql-ok`) which is a required status check. They used to carry `paths-ignore:` and be required by nothing, so a PR could merge with a red image build; the conversion is what let them become required without a filtered-out PR sitting Pending forever. All four call the shared `changed-buckets.yml` reusable workflow rather than each copying the classify job — four drifting copies of the checkout depth or the Go version is the kind of duplication that goes wrong quietly. `supply-chain.yml`'s **`sca-result` is gated on the same bucket as the two OSV passes it reads**, so it never sees a `skipped` dependency: it treats anything other than `success` as failure, skipped included, and that is deliberate — there, a skipped pass means the scan genuinely did not happen. The aggregates accept `skipped` because there it means the classifier established there was nothing to scan. `npm run lint:ci-gate` checks **all four** gates, not just `ci-ok`.
- **`ci.yml` gates from the inside**: a `changes` job runs `go run ./tools/cmd/changed-buckets` and publishes one boolean per bucket, which each job consumes as `if: needs.changes.outputs.<bucket> == 'true'`. Only `gitleaks` is ungated — a secret can land in any file type — and `ci-ok` itself, which must always report. **`ci-ok` is the single required status check** — it `needs:` every other job, runs `if: always()`, and fails unless each reports success *or skipped*, so nothing relies on GitHub's "a skipped job satisfies a required check" behaviour. It also stops the ruleset drifting, which it already had: `helm` and `plumber` were enforced by nothing while `docs/releasing.md` claimed every job was required. `npm run lint:ci-gate` (run by the `actionlint` job) fails if a job is missing from `ci-ok`'s `needs:`.

The mapping, which `ci.yml` states inline beside each `if:`: `test`→`app`, `schemas`→`schemas`, `go`→`go`, `renovate`→`renovate`, `helm`→`charts`, `markdown`→`markdown`, `links`→`links`, `audit`→`deps`, and `actionlint`/`zizmor`/`plumber`→`workflows`. A docs-only PR therefore runs `markdown`, `links`, `gitleaks` and `ci-ok`, and nothing else.

Four rules in `tools/internal/buckets` are load-bearing are load-bearing and easy to "simplify" wrongly. **It fails open** — a non-PR event, a missing parent, any error at all reports every bucket as changed; over-running is cheap, silently skipping a job that should have run is the failure that lets a broken PR through. **Any `.github/**` change runs everything**, because `renovate.json` automerges the workflow tool-version group *on the grounds that* `ci.yml`'s own `actionlint`/`gitleaks`/`zizmor`/`helm` jobs exercise a bump — and a `HELM_VERSION` bump touches only `ci.yml`, so without this rule that PR would automerge completely unexercised. **Only `pull_request` is gated**, so a mis-defined pattern is still caught by the full suite on the `main` push rather than never. And **the `links` bucket is deliberately wider than `markdown`** (it includes `charts/`, `docs/` and `LICENSE`) because `lint:links` resolves relative links that point *out* of markdown — moving `docs/img/capacity-latency.svg` breaks one. It diffs `HEAD^1..HEAD` on the PR merge ref rather than trusting `github.event.*.sha`, and uses `--no-renames` (rename detection prints only the destination path, hiding exactly those moves).

**Every one of those four rules is pinned by a test, and the classifier's whole behaviour is pinned by a golden file** (`tools/internal/buckets/testdata/bucket-golden.tsv`). That file is not hand-written: each row was produced by running the *bash* implementation this replaced, inside a throwaway repo with a real merge commit, and `TestGoldenParity` asserts the Go port classifies identically. It could only be captured once, since the script is deleted in the same change — so don't regenerate it, and treat a diff against it as a behaviour change to justify rather than a fixture to refresh. The three patterns that named files under `scripts/` now name `tools/`, which the force-everything rule already covers; `TestMovedScriptsOnlyEverRunMore` asserts that substitution never *narrows* what runs, because running fewer jobs than before is the one direction that can let a broken PR through.

`just ci` still runs **everything, unconditionally** — the gating is a CI-only concern, and a local run you asked for should not second-guess you. That is the one place the justfile deliberately diverges from the workflows it mirrors.

## The `tools/` Go module

**The CI logic that had real parsing in it is Go, in one module at the repo root** (`go.mod`, sources under `tools/`), invoked everywhere as `go run ./tools/cmd/<name>`. `ci.yml`'s `go` job is the only thing that compiles it: `gofmt -l` (must print nothing), `go build ./...`, `go vet ./...`, `go test ./...`, mirrored exactly by `just go` and folded into `just ci`.

| Command | Replaces | Run by |
|---|---|---|
| `changed-buckets` | `scripts/changed-buckets.sh` | `ci.yml`'s `changes` job |
| `scan-gate trivy\|osv` | two inline Python blocks in `container.yml` **and** the copy in `just image-sca` | `container.yml`'s `scan`/`sca`, `just image-scan`/`image-sca` |
| `validate-schemas` | `scripts/validate-json-schemas.mjs` | `npm run lint:schemas` |
| `check-ci-gate` | `scripts/check-ci-ok-covers-every-job.mjs` | `npm run lint:ci-gate` |
| `check-markdown-links` | `scripts/check-markdown-links.sh` | `npm run lint:links`, `link-check.yml` |
| `helm-loadtest` / `helm-capacity` | `scripts/helm-*.sh` | `just loadtest`, manual |

**What deliberately stayed bash**, and why: every tool install (`curl` + `sha256sum -c` + `tar`), the buildah/podman/skopeo orchestration in `container.yml`'s `build` job, and every one- or two-line `run:` step. Go there would be more code that still shells out to the same binaries, with a compile step in front of it. The rule that decided each case was *is there parsing or branching logic here that can be wrong quietly* — a checksum verification fails loudly, a severity gate does not.

Two consequences worth knowing before editing:

- **`container.yml`'s `scan` and `sca` jobs now sparse-check-out `tools/`, `go.mod` and `go.sum` alongside their acceptance file.** They still do not check out the repo — `src/`, `charts/`, `docs/` and `.github/` are never fetched — so the original property holds: those jobs cannot accidentally scan working-tree sources instead of the image. That sparse checkout is the entire reason the OSV gate is no longer written twice.
- **The Go toolchain version is pinned as a literal `go-version: '1.27.1'`** in `ci.yml`, `container.yml` and `link-check.yml`, grepped out of `ci.yml` by the justfile (`go_version`) exactly as `node_major` and every tool version already are, and bumped by a `renovate.json` custom regex manager. `go.mod`'s own `go` directive and the module's dependencies are the separate `gomod` manager — **that group is not automerged**, unlike npm minor/patch, because this module *is* the gates rather than something the app ships.

Dependencies are two, both with a reason: `gopkg.in/yaml.v3` (parsing `ci.yml` for the `ci-ok` check — there is no YAML parser in the standard library) and `github.com/santhosh-tekuri/jsonschema/v6` (real draft 2020-12 validation, replacing ajv). **`ajv` was dropped from `package.json` entirely**, along with its now-dead `fast-uri` override, since nothing else in the tree depended on it — and `ci.yml`'s `schemas` job no longer runs `npm ci` at all.

`tools/internal/scan` is where the severity bar lives, once, for both engines: **a finding blocks only if it is HIGH/CRITICAL *and* fixable**. Three things there are load-bearing. Neither reader knows anything about dates — both scanners are run with their own acceptance file, which removes an accepted finding from the JSON before it is ever parsed, and that is exactly what keeps "a deadline, not a dismissal" working with no code to maintain. `--ignore-unfixed` applies to **vulnerabilities only**, so a HIGH/CRITICAL *secret* still blocks despite having no fixed version — filtering the credential baked into an image would be the worst possible thing to filter. And OSV's `max_severity` lives on the **group**, not the vulnerability, so it has to be mapped back onto every id in that group before any per-finding decision. The fixtures under `tools/internal/scan/testdata` are real captured output from the pinned Trivy and OSV-Scanner against a real image, including a genuine before/after pair for the acceptance files; that directory's `README` says how each was produced and why the one hand-written fixture is hand-written.

**`Containerfile.redhat` is built and scanned by the same jobs, as a two-entry matrix** (`alpine`, `redhat`) on `build`/`scan`/`sca`; artifact names and SARIF categories take a `-redhat` suffix on the second leg and stay unsuffixed on the first, so the Alpine image keeps its code-scanning history. GitHub Actions can't share one matrix literal across jobs without a job that exists only to emit it, so the list is written out three times — adding a variant means editing all three. **`publish` is deliberately not a matrix: only the Alpine image is pushed.** Neither scanner here can read the Red Hat image (Trivy: OS family `none`, 0 packages; OSV-Scanner: "No package sources found") because Project Hummingbird's `/etc/os-release` says `ID="hummingbird"`, which no distro map knows yet and neither tool falls back to `ID_LIKE` for — Syft catalogues its 45 rpms fine and Grype scans it, so it's a scanner gap, not an unreadable image. Don't paper over it with `trivy --distro redhat/10`: it enumerates the packages but compares `.hum1` versions against RHEL advisories, so it always looks clean. `scan` warns when a scan enumerated nothing and `sca` skips its upload and gate rather than posting an empty, authoritative-looking SARIF — and the dated acceptance files below are, for the same reason, an Alpine-image mechanism today.

**Both scan jobs read a dated acceptance file** — `.trivyignore.yaml` (`expired_at`) and `osv-scanner.toml` (`ignoreUntil`) — for CVEs whose only fix is a base-image bump this repo doesn't control. They expire on a date and the build goes red again, which is the point: this is a deadline, not a dismissal. Three traps, all documented in `docs/container.md`: Trivy auto-discovers only the plain `.trivyignore` (no expiry), so the `.yaml` must be named with `--ignorefile`; neither scan job checks the repo out (each sparse-checks-out just its own acceptance file plus the `tools/` module that gates on it); and the two files are **not** copies of each other — Trivy tends to report a base-image issue as one CVE where OSV splits the same package's Alpine advisories into several `ALPINE-CVE-*` ids, so an id added to one covers nothing in the other. **Both ship empty**, which is the intended steady state: an entry belongs there only when the fix is genuinely outside this repo (anything a dependency bump fixes gets bumped — see `package.json`'s `overrides`). `container.yml` also runs **weekly on a cron**, because an expiry date means nothing unless something runs to notice it.

`charts/yaml-config-generator-validator/` is a Helm chart that deploys the container image into Kubernetes — a third hosting option beside GitHub Pages and plain podman, see `docs/helm-chart.md`. Standard layout (`Chart.yaml`, `values.yaml`, `templates/`, `_helpers.tpl` prefixed `ycgv.`), with Ingress/HPA/PDB/NetworkPolicy all optional and off by default. Two things about it are load-bearing and easy to "fix" wrongly: **there is no `runAsUser`** — `runAsNonRoot: true` plus the numeric USER each image already declares covers both variants (101 for Alpine, 65532:0 for Red Hat) and is what keeps it deployable on OpenShift, where the `restricted-v2` SCC assigns its own UID and rejects a pod that asks for one — and **`/tmp` is an `emptyDir` because it is the only path nginx writes**, which is what makes `readOnlyRootFilesystem: true` real rather than aspirational. `ci.yml`'s `helm` job runs four tools, each answering a different question: **helm-unittest** (does it render what the values say? — `charts/*/tests/*_test.yaml`, and the only one of the four that connects an input to an output; it runs first), `helm lint` (well-formed chart?), kubeconform `-strict` against the real Kubernetes schemas (valid object? — helm lint alone passes a Deployment with a misspelled field), and kube-linter (sensible object? — kubeconform is perfectly happy with a valid Deployment that runs as root; SARIF → code scanning). **The other three are all structural**: each stays green on a chart whose values have quietly stopped reaching the manifest, which is the whole reason the unit tests exist. They pin down the decisions this paragraph calls load-bearing (no `runAsUser`, the `/tmp` emptyDir, digest-beats-tag, `replicas` omitted under an HPA, the Service targeting the container port *by name*, "renders nothing by default" for all four optional objects) plus the measured resource numbers, so changing a default means changing a test. Writing them found one real bug: `app.kubernetes.io/version` was passed through from `Chart.AppVersion` unsanitised despite a comment claiming otherwise — a label value admits only alphanumerics/`-`/`_`/`.` while an appVersion may carry a `+` or a `:`, and an invalid label makes the API server reject *every* object the chart renders. The default `appVersion` is `latest`, so no ordinary render exercised it. helm-unittest is a Helm **plugin**, not a binary: it is installed by extracting the release tarball into `HELM_PLUGINS` and checking it against the release's own checksum file (never `helm plugin install`, which refetches unverified and runs the release's install hook), and the justfile prepends its pinned copy to `HELM_PLUGINS` exactly as it prepends `.ci-tools/<platform>/bin` to `PATH`. Every `charts/*/ci/*-values.yaml` is rendered through all of them too, since the optional templates are off in the defaults — two of the findings that shaped the chart only appeared once they were on. The chart's `.helmignore` excludes `tests/` and `ci/` so neither the suites nor the fixtures' example hostnames end up inside a packaged chart. `.kube-linter.yaml` excludes exactly three checks, each with its reason in the file (`latest-tag`, `no-anti-affinity` — the chart uses `topologySpreadConstraints` — and `non-existent-service-account`, an artifact of the `serviceAccount.create=false` fixture); everything else it reports gets fixed, as `unhealthyPodEvictionPolicy` was. kube-linter is also the one tool here not checksum-verified from a release file, because it publishes none: its install reads the asset's sha256 from GitHub's release API, which a Renovate bump updates by itself. `just helm` runs the same four locally, in the same order. **The chart's `resources` are load-tested, not guessed** (`tools/cmd/helm-loadtest`, `just loadtest`, numbers and method in `docs/helm-chart.md`): steady-state memory is ~5Mi and the small-page workload survives a 4Mi limit, which is a trap — serving the ~500KB JS bundle to 100 connections peaks at 36Mi of working set and **OOMKills at a 32Mi limit**, so don't drop `limits.memory` below 64Mi on the strength of an idle reading. CPU is the opposite: every CPU limit down to 20m served every request (throttling degrades, it never drops), while p99 rose 50× from unlimited to 50m — hence no CPU limit by default. For platforms that mandate both limits, `tools/cmd/helm-capacity` and `ci/both-limits-values.yaml` carry the measured answer (`cpu: 500m` / `memory: 256Mi` at high concurrency): doubling 500m→1000m buys 23% throughput where 250m→500m more than doubles it, and **more CPU is what triggers the OOM** — a faster pod holds more responses in flight, so at 1 000 connections 128Mi died 4 runs in 5 at 1000m while 500m never did. The two limits are not independent dials. nginx also runs one worker per *node* CPU regardless of the limit, and the base image's autotune script can't fix it because `readOnlyRootFilesystem` blocks it from rewriting nginx.conf.

`.size-limit.json` sets a size budget on the built output, checked by `lint:size`, split into three separately-checked entries: **App shell** (`dist/assets/index-*.js`, the main bundle - React, Zod, the `yaml` package, all app code except the YAML editor; ~128 KB gzipped, limit 145 KB), **YAML editor (lazy-loaded)** (`dist/assets/YamlEditor-*.js`, CodeMirror - loaded via `React.lazy`/`Suspense` from `ConfigWorkspace`, so it's not in the initial page-load bundle; ~103 KB gzipped, limit 115 KB), and **CSS bundle** (`dist/assets/*.css`; ~2.6 KB gzipped, limit 5 KB). The split exists so the app shell's number stays an honest "lightweight" figure even though CodeMirror alone is nearly as large as the entire rest of the app combined. Bump either limit deliberately if a real feature needs it; don't just raise it to make a failing check pass without checking why the bundle grew.

**The app shell is ~99% dependency, and that has been measured rather than assumed** - isolating each vendor into its own chunk gives react+react-dom+scheduler **57.6 KB**, the `yaml` package **30.5 KB**, Zod **22.4 KB**, and *all* app source **15.4 KB** gzipped. There is no accidental inclusion to remove, which is why the limit moved to 145 KB rather than the bundle moving: at 128/130 the budget was one dependency bump from red, and a budget that fails for reasons nobody can act on gets raised reflexively, which is the failure mode the paragraph above warns about. Two ways to buy real headroom were measured and **deliberately not taken** - record them here so the next person doesn't rediscover them:

- **Lazy-load `ConfigWorkspace`/`KubernetesWorkspace`** the way `YamlEditor` already is, moving the `yaml` package (30.5 KB) out of the shell - `OnboardingWorkspace` is the front door and touches no YAML. Rejected for now because `App.test.tsx`, `App.a11y.test.tsx` and `App.colorblind.test.tsx` all `render(<App />)` synchronously and assert against the real rendered trees; every one would have to become `findBy*`, and the a11y suites are the last thing to make more indirect.
- **Migrate to `zod/mini`.** Zod's JSON-Schema *output* path (`to-json-schema.js` + `json-schema-processors.js`, ~57 KB of source) is bundled today via the `import { z } from 'zod'` barrel and is dead - this app converts JSON Schema *into* Zod, never the reverse, and `toJSONSchema` appears nowhere in `src/`. The used API surface is small enough to port (`array`/`boolean`/`enum`/`number`/`object`/`string`/`discriminatedUnion`/`literal`). Rejected because it is worth only ~4-10 KB and rewrites the validator construction that *is* this product.

`Containerfile` + `container/nginx.conf` + `.containerignore` build an OCI image (~15 MB) that serves the built `dist/` from `nginx-unprivileged` — an alternative to GitHub Pages for self-hosting, not part of how the site itself ships.

**`Containerfile.redhat` is a second, equal image** — same site, same `container/nginx.conf`, built and served entirely on Red Hat Hardened Images (Project Hummingbird: `registry.access.redhat.com/hi/nodejs:24-builder` → `hi/nginx`, public, no subscription). It exists because a RHEL lineage is a hard requirement in plenty of places, not a preference. ~53 MB, glibc not musl, distroless runtime (no shell, so nothing can `exec` into it — including CI, hence the `podman top` UID check), `USER 65532:0` (**not** `65532:65532` — Hummingbird follows the OpenShift arbitrary-UID/group-0 convention and several nginx directories are group-0 writable; pinning the group builds an image that can't start), and one extra config file, `container/redhat-temp-paths.conf` → `/etc/nginx/conf.d/00-temp-paths.conf`, repointing nginx's five temp paths at `/tmp` because `hi/nginx` keeps them under `/var/lib/nginx/tmp` owned by UID 999 mode 0770, which 65532 cannot write even on a writable rootfs. It declares no `CMD`: the base's `ENTRYPOINT` is already `/usr/sbin/nginx` and a second `CMD` would be appended to it. Neither image is canonical; `container/nginx.conf` is shared verbatim and both are built, smoke-tested, scanned and published. Written for `buildah bud` and deliberately restricted to plain OCI-compatible instructions (no `# syntax=` directive, no `RUN --mount` cache mounts, no `HEALTHCHECK` — that last one is a Docker-format extension buildah drops unless built `--format docker`; `/healthz` in the nginx config exists for orchestrator probes instead), so podman/docker build it identically. Non-root in both stages, `npm ci --ignore-scripts`, root-owned web root, port 8080, every base digest-pinned like every `uses:` (Renovate's `dockerfile` manager, added to `enabledManagers` — its default file patterns already match `Containerfile.redhat`). `container.yml` is what keeps it honest — see above and `docs/container.md`.

## Architecture

**Every config type is authored as a standard JSON Schema file, not TypeScript.** `src/configs/schemas/*.schema.json` are real JSON Schema documents (`https://json-schema.org/draft/2020-12/schema`) — the `title`/`type`/`properties`/`required`/`minLength`/`maxLength`/`pattern`/`enum`/`minimum`/`maximum`/`items`/`minItems` keywords mean exactly what the spec says. A tiny converter (`src/configs/json-schema.ts`) derives *both* the Zod validator and the form's field list from the same JSON Schema document at build time, so there is no separate hand-written schema to keep in sync — see `docs/adding-a-schema.md` for the authoring guide (keyword reference, worked examples, what's deliberately not supported).

`src/configs/index.ts` auto-discovers every `*.schema.json` file via `import.meta.glob` and builds a `ConfigDefinition` from each — **dropping in a new `.schema.json` file is the entire integration, no other code needs to change** (add its `x-config-id` to `DISPLAY_ORDER` only if it needs a specific pill position rather than landing at the end).

### The config registry (`src/configs/`)

- `src/configs/json-schema.ts` — the JSON-Schema-subset types (`ConfigJsonSchema`, `JsonSchemaProperty`, `JsonSchemaComputedGroup`) and `configDefinitionFromJsonSchema(schema)`, which builds the Zod validator (`zodFromObjectProperties`/`zodFromProperty`) and the `FieldDescriptor[]` (`fieldsFromProperties`/`fieldFromProperty`) from one JSON Schema document. **A `"string"` property not listed in its object's `required` array becomes a `toggle-text` field, not a plain optional text box** — tick a checkbox to reveal a text input; unticked, the key is entirely absent from the output. **A root-level `x-computed-groups` entry replaces a set of target properties with one `computed-toggle-group` field** — one shared base text input plus a checkbox per target; the target's real value is computed as `${base}-${suffix}`, never typed directly. This is the mechanism behind `ci.schema.json`'s `registryDocker`/`registryMaven`: the user types a registry name once, ticks Docker/Maven independently, and can't set either computed value to anything other than `base-docker`/`base-maven`. `x-*` keys are vendor extensions (spec-legal - unknown keys are ignored by any conforming validator) covering what JSON Schema has no keyword for: `x-config-id`/`x-default-filename`/`x-computed-groups` (root-level), `x-widget: "select-or-text"` (an enum is *suggested* options, not a strict `z.enum()` - any string within `maxLength` is valid; used for tenant), `x-placeholder`, `x-item-label` (the noun in a `list-object` array's "Add ___" button).
- `src/configs/types.ts` — `FieldDescriptor` (a small declarative union: `text`, `number`, `boolean`, `select`, `select-or-text`, `list-string`, `list-object`, `toggle-text`, `computed-toggle-group`) and `ConfigDefinition<T>` (`{ id, label, defaultFilename, schema, fields }`) - this is the runtime contract `json-schema.ts` produces and everything else (`FieldRow`, `ConfigWorkspace`) consumes; it doesn't know or care that its data came from JSON. Also the draft-handling helpers every config type shares:
  - `emptyDraftFor(definition)` — seeds a fresh draft: one blank row per list field, the first option for selects/`select-or-text` (so e.g. tenant opens on "Existing: acme" rather than a blank "New" box), `null` for `toggle-text` (unticked), `{ base: '', ticked: {} }` for `computed-toggle-group`.
  - `draftToCandidate` / `parseDraft(definition, draft)` — strips untouched blank rows (a list-string entry that's just whitespace, a list-object row where every text/select field is blank — booleans/numbers don't count toward "blank", see `objectHasContent`) before running the zod schema, so an untouched list field doesn't spam "required" errors before the user has typed anything. Also drops a `toggle-text` field entirely from the candidate object when its value is `null` (rather than passing an empty string through), and fans a `computed-toggle-group`'s single draft key out into each ticked target's own real key (`${base}-${suffix}`, or `''` — not the garbled suffix — if the base is still blank) — the group's own synthetic key never appears in the candidate at all.
  - `draftFromCandidate(fields, candidate)` — the inverse of `draftToCandidate`: rebuilds a full draft object from schema-validated data (e.g. parsed pasted/fetched YAML), notably reconstructing a `computed-toggle-group`'s `{ base, ticked }` shape from whichever of its targets' fanned-out keys are present, rather than resetting the group blank.
  - `draftHasContent` — used only for the pill status dots (see below).
- `src/configs/schemas/{tenant-config,ci,cd,env,protection}.schema.json` — one JSON Schema document per file type. The tenant `enum` (existing tenant names) lives directly in `tenant-config.schema.json`'s `tenant` property - edit it there when tenants are added/removed (each must stay ≤ 12 chars, matching `maxLength`).
- `src/configs/index.ts` — glob-discovers the schema files, builds `CONFIG_DEFINITIONS` (sorted by `DISPLAY_ORDER`, unlisted ids appended at the end), `getConfigDefinition(id)`, and `getDraftStatus(definition)` (reads a type's persisted draft straight from `localStorage`, without mounting its form, to badge pills for types that aren't currently open).

**What the JSON Schema subset deliberately does not support**: `$ref`, `oneOf`/`anyOf`/`allOf`, conditionals (`if`/`then`), computed/derived fields (a field whose value is calculated from other fields rather than typed in), and cross-field validation (a `.refine()`-style rule spanning multiple properties). None of the current five config types need any of these. If a real requirement needs one, it's a deliberate extension to `json-schema.ts` (and worth discussing the design first) - not something to fake with a placeholder field.

### Generic form rendering (`src/components/fields/FieldRow.tsx`)

One recursive component renders every field type for every config, driven purely by its `FieldDescriptor`. `list-object` fields (e.g. `githubTopics`, env `variables`) recurse into `FieldRow` for each item field with `compact` set, so item rows render as one inline strip (select/inputs/checkbox side by side) rather than stacked labeled blocks. `select-or-text` (currently only tenant) renders an Existing/New radio pair; the "New" input's `maxLength` comes from the field descriptor. `toggle-text` renders a checkbox that reveals a text input only when checked; unchecking clears the value back to `null` rather than just hiding a stale string. `computed-toggle-group` renders one shared base input plus a checkbox per target - there is no text input for a target's own value, since the user never sets it directly.

`FieldRow.test.tsx` covers every one of these variants via `@testing-library/react` (render + `fireEvent`, asserting on the `onChange` calls) — when adding a new `FieldDescriptor` type, add its case there too. One gotcha hit while writing these: `getByDisplayValue`/`findByDisplayValue` unreliably match multiline `<textarea>` content in this jsdom setup - use `expect(el).toHaveValue(...)` instead (see `ConfigWorkspace.test.tsx`).

### `ConfigWorkspace` (`src/components/ConfigWorkspace.tsx`)

Three pieces are shared with `OnboardingWorkspace` rather than duplicated: `useGithubTarget(path)` (the persisted owner/repo/branch, the derived location, and the render-time staleness comparison behind the existence check - not a syncing effect), `GithubTargetCard` and `GithubPushLinks` (the three create/edit hint blocks, including the copy-to-clipboard-on-click). `issuesFor` moved to `src/lib/yaml.ts` as `yamlIssueMessages`, which already owns `ParseYamlResult`.

Takes a `definition: ConfigDefinition` prop and contains zero schema-specific logic — `App.tsx` remounts it with `key={definition.id}` when the user switches pills, which is also what gives each config type its own isolated `usePersistedState` drafts (see below) without any shared-state plumbing.

`draft` (`Record<string, unknown>`, `usePersistedState`-backed, one field per key) is the single source of truth; the right column's unified YAML field (`{ yamlText, feedback }` state) is a *view* of it, kept in sync bidirectionally:

- **Form → text**: a `useEffect` on `[definition, draft]` re-derives `yamlText`/`feedback` from `parseDraft(definition, draft)` on every draft change (via `FieldRow` `onChange` → `setField`) - *unless* the YAML field is currently focused (tracked via a ref, not state, so it doesn't itself trigger a render), so a live edit in progress there is never clobbered by this effect racing ahead of the user's own keystrokes.
- **Text → form**: `handleYamlTextChange(text)` (the field's `onChange`, and what "Fetch from GitHub" calls with the fetched content) runs `parseYaml(definition.schema, text)`. On success, `draftFromCandidate(definition.fields, parsed.data)` rebuilds a full draft object (the inverse of `draftToCandidate` - notably reconstructing `computed-toggle-group` values from their fanned-out target keys, which a naive `{ ...emptyDraftFor(definition), ...parsed.data }` spread can't do, since that field's own key never appears in validated data) and replaces `draft` with it. On failure, `draft` is left completely untouched and the parse errors are shown - typing invalid YAML never resets or partially overwrites the form.
- There's no separate "Validate" or "Load into form" button - both validation and form-sync are continuous. A one-line `aria-live` status readout ("✓ Valid — synced to form" / an error list) replaces them.
- Pasting/fetching YAML with keys not in the schema silently drops those keys once it round-trips through `draft` (Zod's non-strict `z.object()` from `zodFromObjectProperties` already stripped unknown keys on every validate - this is now just continuously visible instead of only after a one-time "Load" click).
- Push to GitHub (footer of the YAML panel, alongside Copy YAML) is unchanged from before: `checkFileExists` → create/edit link, same as documented below - it now reads `yamlText` instead of a separately-computed `yaml` variable.

### The YAML field (`src/components/YamlEditor.tsx`)

A hand-wired CodeMirror 6 wrapper (`@codemirror/state`/`view`/`language`/`lang-yaml`/`commands` - no `@uiw/react-codemirror`, no `codemirror` meta-package, both of which pull in unused autocomplete/search/theming) - line numbers, YAML syntax highlighting, undo/redo. Props are `value`/`onChange`/`onFocus`/`onBlur`/`placeholder`; internally, the `EditorView` is created once per mount (callbacks are read through refs so it never needs recreating) and a separate effect does a controlled-value sync that only dispatches a change when the incoming `value` differs from the editor's current document, so the user's cursor is never disturbed by their own typing round-tripping back down as a prop. Colors are set via `EditorView.theme()`/`var(--...)` CSS custom properties, so light/dark mode is driven by the same `prefers-color-scheme` block in `App.css` the rest of the page uses - no separate theme object.

**Lazy-loaded**: `ConfigWorkspace` imports it via `React.lazy` + `Suspense` (fallback: a plain read-only `<textarea>` showing the current `yamlText`), since CodeMirror is by far the single largest dependency in this app - see the `.size-limit.json` note above.

**Inline error squiggles are a deliberate stretch goal, not implemented** - Zod issues carry an object-key `path`, not a source line/column; mapping one to the other would go through the `yaml` package's `parseDocument(source, { keepSourceTokens: true })` + `doc.getIn(path, true)?.range` (character-offset ranges, confirmed via `yaml`'s own type definitions) feeding `@codemirror/lint`'s `Diagnostic.from`/`.to`. Current behavior: the same validation-error list `ConfigWorkspace` already renders below the field.

`ConfigWorkspace.test.tsx` mocks `YamlEditor` with a plain `<textarea>` sharing its exact props contract, since CodeMirror's real DOM (contenteditable, not a native input) isn't reliably driven by `fireEvent.change` under jsdom - these tests exercise `ConfigWorkspace`'s own bidirectional sync logic, not CodeMirror's internals. `YamlEditor.test.tsx` covers the real component directly, but only what the wrapper itself is responsible for (mount, the controlled-value sync effect, focus/blur forwarding, unmount cleanup) - not realistic keystroke-driven typing, which jsdom's contenteditable support doesn't simulate reliably either. `ConfigWorkspace.test.tsx` and `App.test.tsx` cover the interactive flows end-to-end (filling fields → live YAML field, typing/pasting valid or invalid YAML → form sync or errors, mocked-`fetch` Fetch-from-GitHub and Get-GitHub-link, pill switching + persisted selection) - this is the only place that actually renders the component tree and simulates user interaction; everything else under `src/configs`/`src/lib` tests pure functions directly. `src/test-setup.ts` wires up `@testing-library/jest-dom`'s matchers and stubs `navigator.clipboard.writeText` (jsdom doesn't implement the Clipboard API, and both Copy YAML and the update-link click call it).

### The onboarding checklist (`src/onboarding/`)

The front door, and the only pill that generates nothing. A checklist of imperative steps the user ticks off (ticked rows strike through and go green), authored as data - `src/onboarding/*.onboarding.json`, glob-discovered exactly like `*.schema.json`, so **dropping in a file is the entire integration**. See `docs/adding-onboarding-steps.md` for the authoring guide.

**It is deliberately not the `.workspace` two-column grid** (`.onboarding`, a single 720px centred column): there is no file to render beside the steps, so the steps are the page. No GitHub target card, no YAML field, no Fetch/Copy/Push - a step's output lives on the pill its `config` action points at.

**The CLI/UI switch is the other half of the design.** A step's `actions` are path-independent (docs, tickets, a jump to another pill); its `cli` and `ui` blocks each hold an ordered `instructions` sub-list plus their own actions, and `ui` additionally carries a `console` **path**. The reader picks a route once (persisted under `step-path`, defaulting to `cli`) and **sees only that route** - hiding rather than reordering was the explicit choice, so a reader who asked for clicks never scrolls past a wall of commands. **But it only hides when there's a choice to make**: a step documenting just one route shows that route whichever way the switch is set, tagged `CLI only`/`UI only`, because some steps genuinely have one route (you can't request repo access from a terminal; bootstrapping a checkout is commands and nothing else) and hiding it would leave the step looking like it needs nothing done to it. The switch reads **Command line / UI**, deliberately generic - a step's UI route is frequently not the console at all but a Jira form, an access portal, GitHub's web editor. `x-console-label` names the console on the *link*, where it really is one specific console. Two rules follow from this and are enforced in *both* `src/onboarding/types.ts` and `tools/internal/schemacheck` (the meta-schema can't express either, being semantic): **a `command` action may never sit in the path-independent `actions` list** (it would reach a UI reader, defeating the switch), and a `configId` is checked wherever it appears, including inside `cli.actions`/`ui.actions`.

- `src/onboarding/types.ts` - the Zod schema for the file, with the TS types derived via `z.infer` so there's one description of the shape, not two. A step is `{ id, title, detail?, optional?, actions[], cli?, ui? }`; `title` is **imperative mood** by authoring convention (not machine-enforceable). `actions` is a discriminated union - `docs`/`link` (external link), `jira` (ticket key), `command` (inline `<code>` + Copy button), `config` (a button switching to that pill) - so a step carries as many or as few as it needs and **a Jira ticket is optional, not a required field on every step**. Everything here is `.strict()`, unlike the config side's non-strict `z.object()`: these are hand-authored files, where a typo'd key is a mistake to report rather than an extra to quietly drop (the meta-schema's `additionalProperties: false` says the same thing to CI). Also `checklistSchema`, the browser-local state shape: `{ tenant, product, completed: string[] }`, in which **nothing is required** - it is progress, not a file anyone commits, so its only jobs are surviving a reload and being read back safely when what's in storage turns out to be junk.
- `src/onboarding/onboarding.meta.schema.json` - the JSON Schema each file's `$schema` points at, so a step author gets editor autocomplete, and `lint:schemas` gets something to validate against. It duplicates the Zod shape deliberately; that duplication buys the autocomplete, which is the point of authoring the process as data.
- `src/onboarding/index.ts` - the glob (parsed through Zod at module load, so a malformed file throws loudly rather than half-rendering), `ONBOARDING_DEFINITIONS`, `readChecklist`, and `getOnboardingStatus`, which mirrors `getDraftStatus`'s valid-first precedence so the sixth dot promises the same thing as the other five: green = every non-`optional` step ticked **and** tenant and product both filled.
- `src/onboarding/checklist.ts` - `orderedCompleted` and friends. `completed` is a **list of ticked ids**, not a map of id→boolean: a step added to the file is simply absent and therefore unticked, and a step removed stops rendering, both with no migration code. Ticked ids are stored in declared step order so storage is stable rather than reordering as the user ticks around, and an id matching no step is **preserved and appended rather than dropped** - a step-id rename-and-revert shouldn't destroy someone's saved progress.
- `src/onboarding/links.ts` - `safeBaseUrl(base, placeholder)` plus the two builders on top of it, `jiraUrlFor(base, key)` and `consoleUrlFor(base, path)`. **Two user-typed base URLs now feed `href`s** (the Jira host and the web console host), which is exactly why the protocol allowlist lives in one function: `safeBaseUrl` returns `null` for a blank base, the untouched placeholder, an unparseable URL, **or any protocol other than `http(s)`**. That last clause is a security boundary, not hygiene - `javascript:alert(1)` typed into either box would otherwise be a live XSS vector. While there's no usable base, the ticket key or console path renders as plain text rather than a link (the placeholder hosts are domains nobody here controls, so linking there is worse than not linking). Note the asymmetry: a Jira key is `encodeURIComponent`'d (it's an opaque identifier), while a console path is joined (it's a real path, with meaningful slashes) - it comes from the checklist file, not from the user.

  **Console links open in a new tab, and the UI route says so.** There is no web API for split view - a page cannot put the browser into split-screen; it's a browser/OS feature the reader triggers. Rather than approximate it with `window.open` geometry (which browsers may ignore, and which mobile ignores entirely), the page states the constraint in one line.
- `src/onboarding/seed.ts` - `seedConfigDrafts(values, targets = SEED_TARGETS)`, behind an explicit **Seed config drafts** button. Writes tenant/product into each destination's persisted `draft:<id>` via `writePersistedState`, leaving every other key alone, and returns only what it actually changed so `describeSeedResults` can report honestly (today **only Tenant Config and Kubernetes have those inputs**, so the copy must not imply it touched every pill). `SeedTarget` is structurally the `{ id, label, fields }` part of `ConfigDefinition`, which is how the Kubernetes pill - inputs but no schema and no file - is a destination without pretending to be a config type. Rules worth not undoing: it matches on key **and** descriptor type (`text`/`select-or-text` only - a `select` would render a value outside its `options` as the *first* option while state held something else, a `toggle-text` would flip a key from absent to present, and a `computed-toggle-group` target isn't in `fields` at all so the write would vanish silently); it skips blank values ("not filled in yet", never "clear everywhere") and unchanged ones; it does **no** `maxLength` check, because a `FieldDescriptor` carries no bounds for a plain `text` field - the honest enforcement is the `maxLength={12}` on the onboarding tenant input itself; and `replaced` is set only when the previous value differs from that field's own `emptyValueFor` default, since an untouched `select-or-text` tenant already holds `"acme"` and claiming to have replaced it would be a lie. **Writing straight to `localStorage` is safe only because `App` mounts exactly one workspace at a time** - rendering onboarding alongside a workspace would let that workspace's persist effect write its pre-seed draft back over the seed. There's a comment saying so.
- `src/components/OnboardingWorkspace.tsx` / `OnboardingStep.tsx` - the centred column described above: a details card (tenant, product, and the two base URLs, plus the seed button and its receipt) and the step list, headed by the route switch. It imports neither `YamlEditor` nor `src/lib/github.ts`. The switch is a real `fieldset` of radios with a visually-hidden legend rather than two `aria-pressed` buttons - exactly one is active, so a radiogroup is what it actually is, and the native inputs keep the browser's own keyboard and screen-reader behaviour instead of a re-implementation.
- `src/components/icons.tsx` - the app's only icons, seven inline SVGs sized by attribute so they stay out of the CSS budget entirely, inheriting `currentColor` for dark mode. The ticket glyph is a **neutral issue mark, not Atlassian's logo** - shipping a third party's trademarked mark in a public static site is a licence question this project hasn't taken on. The word "Jira" beside it is nominative reference and is fine.

### The pill strip (`src/nav.ts`)

The only module that knows both kinds of pill exist. `NavEntry` is a `{ kind: 'config' | 'onboarding' | 'kubernetes' }` union wrapping the registries, so `ConfigDefinition` gained **no** `kind` field (which would have churned every test fixture that builds one) and `ConfigWorkspace`'s prop stayed non-optional. There are exactly two narrowings in the codebase - `navStatus` and the JSX branch in `App` - both exhaustively checked, so adding a fourth kind is a compile error until both are handled. Onboarding leads the strip (the front door) and Kubernetes ends it (an output of the process, not one of the repo's config files); `selected-config-id` is persisted, so ordering only sets the default pill for a fresh browser. `LINKABLE_PILL_IDS` is the set a step's `config` action may point at - everything except the checklist itself.

`getNavEntry(id)` **falls back to the first entry instead of throwing**, unlike `getConfigDefinition`. That fixes a pre-existing crash: the persisted id lives in the user's browser and can outlive the entry it names (rename a schema file), which used to render an unrecoverable blank page. `getConfigDefinition` keeps its throw - every other caller passes a hardcoded id, where a miss is a programmer error. Note `App` compares each pill against the *resolved* entry, not `selectedId`, so a stale id still highlights the pill whose workspace is actually on screen; and it holds a nonce (`refreshStatusDots`) purely so seeding's `localStorage` writes are reflected in the other pills' dots, which `App` can't otherwise observe.

**The Kubernetes pill persists its non-secret inputs and never its output**, and `KubernetesWorkspace.storage.test.tsx` is what keeps it that way. The property is a consequence of how the component is built rather than anything that announces itself — `renderManifests(draft)` runs on every render from `{tenant, product}`, and only those are stored — so the obvious refactor (memoising the manifests into `usePersistedState`) would quietly break it. It matters because the stream contains ServiceAccount **token Secrets**: placeholders today, but the shape invites someone to paste a real one in before applying, and browser storage is readable by any script on the origin and survives the tab closing. The output field is also `readOnly`, so nothing can be pasted into it in the first place. **The inputs are governed by an allow-list, `PERSISTED_KUBERNETES_KEYS`, and the direction matters**: these resources will eventually need a real secret typed in (a registry credential, a pre-existing token), and a deny-list would persist that input by default with the mistake invisible. So `KubernetesWorkspace` deliberately does **not** use `usePersistedState` — that hook writes back whatever the state object holds, which is exactly the wrong default here — and instead narrows through `persistedKubernetesDraft(draft)` on the way out and on the way back in, the latter scrubbing anything an older build already wrote. A new input is therefore non-persisted until someone adds its key to the list, and `src/kubernetes/index.test.ts` pins the list's contents so growing it breaks a test first: adding a key is asserting the value is not a secret. **There are two tiers, and the default is the strict one**: `PERSISTED_KUBERNETES_KEYS` (`localStorage` — `tenant`, `product`, `namespace`) and memory only for everything else, `apiSecret` included. **The API secret is stored nowhere**, and `sessionStorage` was built for it and then taken back out — it is readable by any script on the origin while the tab is open, so against a compromised dependency or an injected script it offers no protection and only adds a window where the value sits somewhere enumerable by key. The cost was accepted explicitly: the secret is gone on reload, on navigating away, and on switching pills (`App` mounts one workspace at a time), and the note beside the field says so rather than letting someone find out by losing a value. `SECRET_KUBERNETES_KEYS` is **derived** from the descriptors' `secret: true` flag rather than listed twice, and a test asserts the two lists never share a key. Its Secret uses **`stringData`, not `data`** (base64 is an encoding, not encryption — encoding it would only make it look protected), is **omitted entirely when blank** (an empty `stringData` would overwrite a real cluster secret with nothing), and carries a **do-not-commit banner inside the YAML** since it is the one output here that must never be committed. **The secret is masked in both places at once** — a `type="password"` field and `api_secret: ••••••••` in the rendered manifest, governed by one Show/Hide button that starts masked every visit and is not remembered. Masking only the input would have been theatre, since the value is rendered in the panel beside it, so the toggle covers both or neither; `FieldRow`'s `revealSecret` defaults to `false`, so a secret field added elsewhere is masked by default. Bullets not asterisks (`*` opens a YAML alias, so a run of them comes back quoted), and a **fixed-length** mask, since a mask matching the real length leaks the real length. **Copying is deliberately exempt**: `Copy all` re-renders unmasked, because copying the mask would create a Secret holding literal bullets and that failure surfaces inside a cluster as an app that cannot authenticate — so what you see is not always what you copy, and both the panel and the post-copy status line say so. `secret: true` also turns off autofill/spellcheck/autocorrect. **Clear secrets** blanks every field marked secret and the output — named for the category, not for today's single field, so a second secret input needs no rename; there is no storage for it to clear, and it exists because the value is on screen until something removes it. **The namespace is `<tenant>-<product>` unless the optional `namespace` field overrides it**, in which case that name is used verbatim and *every* derived object moves with it (ServiceAccounts, their token Secrets, Role, RoleBinding, API Secret) — tenant and product stay required, since they are the identity and still label the Namespace object, and a typed namespace gets the same DNS-1123 check as a derived one. It is on the storage allow-list (a name, not a secret), and adding it there failed the pinned test first, which is that test doing its job. **The related exposure that is not covered, because it is a product decision rather than a bug**: a `ConfigWorkspace` *does* persist its draft and its YAML field *does* accept paste, so anything typed or pasted there reaches `localStorage` — that is the documented "switching types never loses work" behaviour, and changing it is a call for the user, not a fix to make quietly.

### The Kubernetes pill (`src/kubernetes/`)

A step's output is either one of the config files or the cluster resources for the tenant's namespace; this is the latter. **Not a config type**: no schema, no file, nothing to push - two inputs in, a read-only rendered manifest stream out, copied and `kubectl apply`'d. See `docs/kubernetes-resources.md`.

- `src/kubernetes/manifests.ts` - `renderManifests({ tenant, product })`, returning a result union. Builds each resource as a plain object and stringifies it (rather than interpolating into a YAML template string, which would be fragile with free-text input), joins them with `---`, and prefixes each with a static comment so the `# TODO: confirm` markers land in the copied text, not just the UI. Resources: a namespace `<tenant>-<product>`, two ServiceAccounts, a Role, a RoleBinding covering both, and a token Secret per account.
- **Name validation is real, not decorative.** Kubernetes names are DNS-1123 labels and the inputs are free text, so an invalid name is reported instead of emitting YAML `kubectl` will reject. The namespace is checked **first and alone** - every other name derives from it, so a bad character in the tenant would otherwise be reported six times with the fix buried in the repetition - and the derived names are then checked for length *independently*, because a token Secret's name is 6 characters longer than its service account's and a namespace short enough for one can still overflow the other.
- `src/kubernetes/index.ts` - `KUBERNETES_DEFINITION` (`{ id, label, fields }`), whose two `FieldDescriptor`s let `FieldRow` render the inputs and let `src/onboarding/seed.ts` seed them. The draft lives under `draft:kubernetes`, deliberately the same `draft:<id>` convention the config types use, so there's one storage shape rather than two. It also owns `PERSISTED_KUBERNETES_KEYS` and `persistedKubernetesDraft` - the storage allow-list described above, derived from the one constant rather than a second hand-written list, so the pill can grow a secret-bearing input without that input reaching `localStorage`.
- `src/components/KubernetesWorkspace.tsx` - the two-column shell *is* right here (there's real output to pin beside the inputs), but one-way: `YamlEditor` gets a new `readOnly` prop (`EditorState.readOnly` **and** `EditorView.editable.of(false)`, so the field loses its caret and reads as output), and there is no draft-from-YAML path at all.

### Persistence (`src/lib/persisted-state.ts`)

`usePersistedState(key, initial)` is a drop-in `useState` that also syncs to `localStorage` under a namespaced key — purely client-side, works identically on any static host (GitHub Pages included). Keys used: `draft:<configId>` (per-type form draft — `draft:kubernetes` included, see above), `onboarding:<onboardingId>` (checklist progress), `step-path` / `jira-base-url` / `console-base-url` / `theme` (per-reader, not per-tenant: two people onboarding the same tenant may use different hosts, and the CLI/UI and light/dark preferences belong to the person), `github-owner` / `github-repo` / `github-branch` (shared across types — same target repo; owner/repo seed from `inferRepoFromPagesUrl` on first load, see below), `selected-config-id` (last-open pill — now a nav entry id, so it can name the onboarding pill too; the name is kept so nobody's selection resets). There is no key for the file path — it's fixed to `definition.defaultFilename`, not state. `readPersistedState` is the non-hook read used by `getDraftStatus`/`getOnboardingStatus` to badge pills that aren't mounted, and `writePersistedState(key, value): boolean` is the non-hook *write*, added for seeding (it returns `false` when storage is unavailable, so a caller never reports a write that didn't happen; `usePersistedState`'s own effect now goes through it too).

### YAML + schema plumbing (`src/lib/yaml.ts`)

`dataToYaml(data)` (stringify, any shape) and `parseYaml(schema, source)` (parse + `schema.safeParse`, returning a `ParseYamlResult<T>` that distinguishes a YAML syntax error (`yamlError`) from a schema validation failure (`issues: ZodIssue[]`)) are schema-agnostic — every config type calls the same two functions with its own zod schema.

### GitHub integration (`src/lib/github.ts`)

The entire GitHub integration, intentionally with no OAuth, no GitHub App, no token handling; every call is an unauthenticated request to GitHub's public API, so all of this only works reliably for public repos.

- `checkFileExists` first confirms the repo itself is visible unauthenticated (`GET /repos/<owner>/<repo>`) before trusting a 404 on the contents endpoint as "missing" — GitHub returns an identical 404 for "path doesn't exist" and "repo is private/nonexistent", so skipping that repo-level check makes every private repo look like the file is missing (this was a real bug: it reported "missing" for a file that existed in a private repo, hiding the "open file to update" link entirely). Private repos and rate-limited requests both come back as `'unknown'` — there's no way to tell those apart without a token.
- `fetchFileContent` fetches and base64-decodes a file's current content (same public-API/private-repo limitation as above), used by "Load from GitHub".
- `inferRepoFromPagesUrl(href)` reads `{ owner, repo }` off a GitHub Pages URL (`https://<owner>.github.io/<repo>/`, or the `<owner>.github.io` repo itself at a user/org root) and returns `null` anywhere else - localhost, the container image, a custom domain. `ConfigWorkspace` uses it only as the *initial* value of the persisted `github-owner`/`github-repo` state, so hosting the tool from the repo whose configs it edits means those fields arrive filled in, while an edit still sticks and any other host starts blank for the user to fill. It deliberately doesn't guess: a wrong owner/repo would silently aim every push at someone else's repo.
- **The file path is not user input.** `ConfigWorkspace` uses `definition.defaultFilename` directly (rendered as static text in the target card, `.github-path`), since our software only reads each config under one fixed name - a retargeted file is just a file it never reads.
- `buildCreateFileUrl` builds a `github.com/<owner>/<repo>/new/<branch>?filename=...&value=...` link for a new file; `buildEditFileUrl` builds a `github.com/<owner>/<repo>/edit/<branch>/<path>` link for an existing one. **The `/new` page rejects prefilled content if the file already exists** ("A file with the same name already exists"), and the `/edit` page has no equivalent `value=` param to prefill a replacement — GitHub just doesn't support prefilling an update over the URL. `ConfigWorkspace` works around this by requiring the user to hit "Get GitHub link" first, which runs `checkFileExists` and only then reveals the right link (create vs. edit-and-paste-manually vs. both, if existence is unknown). The "open file to update" link's `onClick` also copies the YAML to the clipboard before GitHub's editor opens, so the user only has to select-all-and-paste there — a deliberately small, secret-free automation.

Don't add token-based or OAuth push/fetch flows without checking with the user first — no-auth was explicitly chosen to keep this a public, backend-less tool; full auto-commit (no page visit at all) would need one and was explicitly deferred.

### Other

- Pill status dots (`App.tsx`, `.status-dot` in `App.css`): grey = empty, amber = draft (some content, not yet valid), green = valid. Computed fresh on every `App` render via `navStatus`, so they update when you switch away from a type and back, but not live while you're still typing in the currently open one (an acceptable tradeoff to avoid lifting every pill's state into `App`). The one exception is seeding, which changes *other* pills' dots by design and so forces a re-render explicitly.

## Schema assumptions worth knowing

Tenant Config's constraints were specified by the user narrowly (tenant length, topic method enum) or inferred where the spec was silent; CI/CD/Env/Protection are wholesale placeholders (see above). Check with the user before tightening/loosening any of these further. (All of these live in `src/configs/schemas/*.schema.json` now - this is a summary, not a second source of truth.)

- `tenant-config`: `tenant` required, ≤ 12 chars, either typed new or picked from the `enum` in the schema file; `product` required non-empty; `proxyEntries` list min 1, each matching a (possibly wildcard) domain pattern like `*.github.com`; `githubTopics` list min 1, each `{ method: 'artefact' | 'environment' | 'script', name, description }` (name/description required non-empty).
- `ci`: `{ runtime: 'node'|'python'|'go'|'java', runtimeVersion, buildCommand, testCommand, triggerBranches: string[], registryDocker?, registryMaven? }` — placeholder, except the registry group (real, confirmed requirement): one shared registry-name input, Docker/Maven ticked independently, each computing its own value as `${name}-docker`/`${name}-maven` — the user cannot set either value directly.
- `cd`: `{ environment: 'staging'|'production', deployCommand, requiresApproval: boolean, notifyChannel? }` — placeholder; `notifyChannel` is optional (tick-to-reveal `toggle-text` field) since not every deploy needs a notification channel.
- `env`: `{ variables: { name, value, secret: boolean }[] }` — placeholder.
- `protection`: `{ branch, requiredApprovingReviews: integer (1-6), requiredStatusChecks: string[], enforceAdmins: boolean }` — placeholder.
